Environmental Indices Analysis Platform

Sentinel-2 · any area of interest

Project overview

I wanted vegetation indices to be easy for anyone to compute, not just for someone who writes code. You give it a boundary, a date range and the indices you want, and the platform returns a time series, a trend, an interactive chart and a map you can download. It answers one question for any polygon that Sentinel-2 covers: how has vegetation, or surface water, behaved here over this period? No code is required on your end.

What it does

The platform computes NDVI, EVI and SAVI for vegetation, and MNDWI for surface water, from Sentinel-2 Level-2A imagery found through a STAC catalogue (Microsoft Planetary Computer by default). The area can be a bounding box or an uploaded GeoJSON file. For each index it returns the mean, minimum, maximum and standard deviation of the time series, a linear trend in index units per year, the time series itself with the number of clear days and the clear-sky share of the area for each period, and a time-mean composite map. The map comes as a georeferenced GeoTIFF for GIS software, a titled PNG figure for reports and a transparent overlay for web maps.

How it works

A Streamlit front end sends each request to a FastAPI service. Large areas can take minutes, so the service returns a job identifier straight away and does the work in the background while the interface polls for the result. Dask does the heavy lifting. Everything between the search and the final statistics is a lazy graph, and pixel data is only read when all the results are computed together in a single step.

The order of these steps is deliberate, because several are only correct in this sequence. Masks must come before merging, because the merge keeps the first clear value at each pixel across a day's tiles, and a cloudy pixel that had not been masked could win over a clear one from the overlapping tile. Nodata must be masked before the reflectance offset is added, or an empty pixel would become a reflectance of −0.1 and enter the averages.

What I learned along the way

Every defect I found was in the data processing, not in the web layer. I found them by running the system against real Sentinel-2 data and by writing tests for each one.

  • Unscaled reflectance. Sentinel-2 stores reflectance as integers up to 10,000, and EVI needs values between 0 and 1. With the raw numbers, EVI came out in the hundreds of thousands. Scaling each collection before any index maths fixed it.
  • A hidden offset. Since early 2022 ESA adds 1,000 to the stored values, and a single search can return scenes with different processing baselines. Ignoring the offset inflates every ratio index's denominator. Over a dense forest near Nairobi, mean NDVI rose from 0.33 to 0.55 once I applied it per scene.
  • Reading everything. The engine fetched every band for every index, even when an index needs only two. Fetching only what each index uses halved the run time of a test run, from 121 seconds to 60.5, with identical NDVI.
  • Bounding box, not boundary. For Nairobi County, 36.5% of the bounding box lies outside the boundary, so I added a polygon mask. It is built lazily in blocks, which shrank it inside the task graph from 15.3 MiB to 9.6 KiB.
  • Half a pixel. The library labels pixels by their corners and the GeoTIFF writer assumes centres, which shifted exported maps by 5 m. Every step now uses pixel centres, and a test checks the file's origin.
  • Partial coverage. A county spans several satellite tiles, and each tile only covers part of it. Before merging same-day tiles, clear-sky coverage looked like 38–50% and the January to March NDVI looked like 0.367. After merging, coverage was 75–98% and NDVI was 0.262.

Run time is dominated by download volume. It scales with the area, the number of scenes and the number of bands read, so a year over the same county should take several times longer than three months.

Data handling

Imagery is never stored. Workers read only the pixel windows covering the area, straight from cloud-optimised GeoTIFFs, and discard them after the computation. Inputs are not persisted, results expire after 24 hours, and signed URLs are removed from any error sent back to the client. The polygon is sent to the STAC catalogue as the search geometry, so the catalogue operator can see the area searched.

Known limitations

  • EVI is an approximation for now. The band mapping does not yet register Sentinel-2's blue band, so green stands in for it. NDVI, SAVI and MNDWI are not affected. Adding the band is a one-line change.
  • Projection. Data is resampled to Web Mercator at a nominal 10 m. Ground resolution and area drift away from the equator, so a native UTM grid would be more accurate.
  • Period means. Each clear day counts equally, however little of the area it observed. Weighting by the valid fraction is a possible refinement.
  • Landsat. It is registered but untested and has no per-pixel cloud masking.
  • Not ready for public use. There is no authentication yet, and the job store lives in one process. These must be fixed before a public deployment.

Status

The full stack runs end to end in Docker, with the API and interface as separate services. The Dask cluster can run locally or on AWS Fargate, but I have only tried the local mode on real data. Next I want to run the whole interface against live Sentinel-2 data on a machine with a fast connection, add the blue band, and then deploy to AWS.
