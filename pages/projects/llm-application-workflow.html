LLM Workflow · In use

An LLM-Assisted Application Workflow

Claude · custom skills · LaTeX · Python

Project overview

Applying for PhD positions, fellowships and jobs means writing the same story many times: a CV, a letter and answers to portal questions, each cut to a different advert and page limit. A language model makes the drafting fast. It also makes three mistakes that matter more in an application than almost anywhere else. It drifts from the facts, it quietly drops things to fit a page, and it writes in a voice that is not yours. I built a small system around Claude to keep the speed and catch those mistakes, and I have used it on five real applications.

The problem I was solving

  • Drift. A model rounds a figure, merges two roles or describes a method I never used. Each slip is small, and each one is hard to spot when I am rereading my own work.
  • Quiet cuts. To fit a page limit, it removes an award or a thesis title and does not mention it.
  • A generic voice. The drafts read like a list of achievements instead of an argument made by a person.

My answer was to treat application writing as a small piece of software. Facts live in one verified place. Claude drafts by following written procedures. A script builds every document and another script checks it before I see it. I stay in charge of everything that cannot be undone.

How it fits together

There are five layers. Information moves down from verified facts to finished documents, and two loops move back up: failed checks return to drafting, and facts I confirm return to the knowledge layer.

  • Knowledge. A folder with my profile split by topic, a machine-readable facts.yaml, the source documents (thesis, transcripts, posters), approved answers to recurring questions, and samples of my own writing. Uncertain items are marked [TO CONFIRM]. It also records what I have not done, so a letter can name a gap instead of implying skill I do not have.
  • Agent. Claude, working through five skills: one that orchestrates an application, and ones for CVs, cover letters, portal questions and quality review. A skill is a written procedure, and it holds no facts about me. Every fact is read from the profile.
  • Build and check. Scripts that compile the LaTeX, enforce page limits, check the facts and render each page as an image to look at.
  • Output. One folder per application, with its requirements, a status log, the sources and the PDFs.

Life of one application

The first stage is a recommendation, not a decision. For one job advert, the analysis showed that the role's core requirement, advanced Stata, was missing from my profile. I decided to pass, and no folder was created. That felt like the system working as intended.

Each folder keeps a requirements.md (parts, limits, deadline with its time zone) and a status.md (stage, open items, a dated log). If I come back after a week, I can see at a glance what is done and what is left.

Checking the facts

The checker, check_facts.py, compares every document against facts.yaml and exits with an error if anything fails, so it can gate a build.

  • Forbidden wording. Patterns that must never appear, each with the reason. A superseded figure, a wrong tool name and a method my thesis did not use are all on this list.
  • Identity. Any ORCID-shaped string, email address or phone number must equal the one on file.
  • Dates near titles. A different date range next to a role is a failure. No date at all is only a warning, because titles also appear in prose.
  • CV completeness. Things every CV must contain, such as both thesis titles and every award.
  • Style. Phrases I want to avoid in letters, such as "passionate", are flagged for rewording.

The forbidden list grows from real mistakes. When a draft contained a wrong figure or a misspelt organisation, I fixed it and then added the wording to the list so it could not return.

Looking at the pages

A PDF can compile cleanly and still be wrong. A line runs past the margin, a stray character prints as text, or a page break strands a signature. So looking at the pages is a required step. The build script renders every page to an image, Claude opens each one, and the text is also extracted to confirm that ligatures and symbols survive copying and applicant-tracking systems. If an image cannot be viewed, Claude is told to say so rather than report a check that did not happen.

Getting the voice right

My early drafts were correct and dull. They had bold sub-headings, bullet points inside letters, and paragraphs that strung facts together ("At X, I did Y. I also did Z."). I gave Claude paragraphs from letters I had written before, and wrote down what they share: open with a problem in the field, then show where my interest comes from; build the foundation as connected work in service of an idea; then look forward to what I would investigate. Gaps are stated in one or two plain sentences, and numbers appear only where they make a point, because the CV carries the full figures. The difference shows most in the first sentence. A list-style draft opened with "I am applying for the fully funded PhD position in your lab". The revised one opens with a statement about the problem and reaches the position once it has been set up.

What the checks caught

These are problems that really reached a draft. Each one became a permanent rule.

  • A superseded figure from my thesis, caught by comparing with the thesis. It is now a forbidden pattern.
  • A claim that a model used rainfall and temperature when the thesis used rainfall only.
  • Misspelt names of tools and organisations, caught by review against sources.
  • Tailoring that removed thesis details and awards from CVs. I noticed it myself, and the "kept in full" rule now lives in the CV skill.
  • A stray carriage return that printed as garbage in a CV. Only the page image showed it, which is why visual review is mandatory.
  • A --date option that did nothing. The compiler was silently reading the original file instead of the modified copy. I only saw it by looking at the rendered date. The fix was to put the temporary folder first on the search path.
  • A signature that pushed a statement onto a second page. The page-limit exit code now stops the build.

Where I draw the line

  • I submit every application, send every email and sign in to every portal. The system never stores or enters a password.
  • New facts enter my profile only after I confirm them. If something disagrees, it is flagged, not silently corrected.
  • Gaps are stated honestly. A modelled estimate is never presented as an observed result, a poster is never presented as a publication, and a missing document is never replaced by a different one.
  • Supervisor emails are drafted only when I ask for them.

These rules are written into the skills, so they hold when a session is resumed later or on another device.

What it cannot do yet

  • The fact checker matches patterns. It catches known wrong wording and missing items, but not a new error phrased in a new way. That still depends on the quality review and on me.
  • Visual review depends on the model inspecting page images. It is thorough for layout and is no substitute for me reading the final PDF.
  • The date rule produces warnings in prose, where dates are rarely near titles.
  • Builds on my Mac lack the icon package that the letter template wants, so letters there use text icons unless I rebuild them with my own TeX installation.
  • Deadlines live in the status files and in reminders I set myself, not in the system.

Status

In use on five applications: three PhD positions and two jobs. It also supports interview preparation, with each story written once in situation, task, action and result form and checked against the same facts. Next I want unit tests for the checker, one command that runs every build, check and package step before submission, a question bank for interviews, and a public repository with the scripts, templates and skills, with my personal data removed.
